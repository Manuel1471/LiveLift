# Asset compatibility spike

Can the asset build catch a runtime and registry mismatch without adding a
browser runtime check?

The experiment used esbuild 0.25.4 and Node 26.5.0. A small registry imported
a runtime binding whose name represented an asset revision. The app read the
registry's `views` export, and the experiment also included a lazy view.

An unused named import was removed by esbuild before it diagnosed the
missing export. An explicit re-export linked the named binding and made
both esbuild and the native Node module loader reject the mismatch. The
successful registry could still be bundled with split views. The standalone
hook did not need a new function or branch.

Use the re-export in the entry registry. Derive the symbol from the Hex or
npm version and the SHA-256 of the exact version, a zero byte, and the hook source. The copied runtime and
the npm entry both export the matching symbol as an alias of
`createClientHook`. The lazy chunks are generated by the same invocation and
the bundler versions their URLs. The spike checks the entry registry
against the selected runtime. It does not validate arbitrary files placed
in a deployment after bundling.

The [npm pack reference](https://docs.npmjs.com/cli/pack/) describes the tarball
used for the consumer test. The [TypeScript module reference](https://www.typescriptlang.org/docs/handbook/modules/reference)
describes the conditional declaration export tested with NodeNext.
