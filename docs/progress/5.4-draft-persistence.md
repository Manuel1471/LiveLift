# 5.4 — Opt-in form drafts

This record covers experimental LiveLift. The [decision](../decisions/ADR-0005-session-storage-scope.md)
selects field drafts with normal Phoenix submission. The
[storage spike](../session-storage-spike.md) established tab copying,
storage failures, and the difference between reordering a DOM node and
patching a bound input.

## Implementation

The HEEx compiler validates the draft opt-in and prepares the storage
helper only for views with an opted-in field. The helper stores text
with a version and expiry in `sessionStorage`, keyed by route, island,
form, app scope and field name. It restores the input property without
events and keeps the text through patches for the same identity.
The HTML value attribute and authoritative state keep their canonical
values. The existing form submit path still validates and sends the
current control value.

The test demo uses a bound field so the browser tests can distinguish
the draft value, the canonical value attribute and the state acknowledged
by Phoenix. The app can discard current drafts with an ordinary form
reset. The supported scope and limits are in the [language guide](../language.md#optional-form-drafts).

## Security and lifecycle

Restored text is untrusted. Records have an exact versioned shape and
size and time bounds. Scope, form and field key checks run before
reading a record. Write denial leaves the previous record available.
Access denial falls back to the normal form. The only new browser
input is the stored draft text, which reaches Phoenix through the
existing input validation and submitted form params. The helper uses
DOM properties, no executable HTML or URL, and logs no values.
Keys are arrays of string segments encoded as strings. No new
dynamic object-key surface or state protocol changes are introduced.
An app provides a scope scoped to the current account or session
and record. A tab can explicitly submit its copy of a draft.

## Measurement

Local verification on 2026-11-21 used LiveView 1.2.13 on macOS arm64 (Apple M4),
Elixir 1.20.2, OTP 29, Node 26.5.0, Chromium 158.0.8127.18, Firefox
159.0 and WebKit 27.2. The comparison is against `a099ab7`.

The esbuild-minified shared runtime is 8,179 bytes gzip on both
revisions. `python3 bench/island_bundle.py` measured 55,363 bytes gzip
for the split demo entry and 64,477 for eager loading, compared with
55,364 and 63,490 in 5.3. The reference app from
`bench/phoenix_bundle.sh` was unchanged at 47,351 bytes with Phoenix and
55,842 with LiveLift. The form chunk carries the helper. The class helper changes only for views
already using class commands.

`mix run bench/benchmark.exs`, `bench/phoenix_event.sh` and `npm run dom`
ran as regression checks. The event benchmark used five batches of 200
events per variant and had variable batch medians. The linkedom run
is a DOM-only check.

## Phase 7 — Expiry and record format

The browser check writes a draft of 2,048 emoji using the actual input,
which stores 4,096 UTF-16 code units. It reloads one millisecond before
the deadline and restores the draft. It then edits the field and verifies
that the record's deadline moves 30 minutes from that edit. The next reload
still restores the text at the original deadline. At the renewed deadline,
LiveLift removes the stored record and displays Phoenix's value with no
marked event acknowledged. The fixed wall clock keeps LiveView's timers
running. [Playwright clock documentation](https://playwright.dev/docs/clock#test-with-predefined-time).

The invalid-record check also covers an object-shaped record and an
unknown version of the array record. Both fall back to Phoenix's value.
The object is synthetic and represents an unsupported storage format.

```sh
cd bench
LIVE_LIFT_TEST_DEPLOY=1 npm run e2e -- e2e/form_drafts.spec.mjs
LIVE_LIFT_TEST_DEPLOY=1 LIVE_LIFT_FORCE_TEMPLATE_FALLBACK=1 npm run e2e -- \
  e2e/form_drafts.spec.mjs --grep 'opt-in draft expires|ignores invalid records'
```

Against baseline `974fb30`, 15 checks with digested assets and six more
with the fallback parser forced passed in Chromium, Firefox and WebKit.
The updated workflow selection passed 15 local checks with digested
assets, including the exact expiry test. These checks exercise
restoration after navigation in the same tab using a controlled clock.

In a scratch build, changing the expiry comparison from `>` to `>=`
made the Chromium check fail at the renewed deadline. It saw the draft
text where the server value should have appeared. The runtime in the
verified build uses the original comparison.
